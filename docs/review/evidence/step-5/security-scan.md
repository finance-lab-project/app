## Threat Model

Finance Lab is a single-account Java/Vaadin application with an anonymous browser-local Budget planner, native Servlet login/logout and transfer endpoints, and an authenticated Vaadin planner backed by PostgreSQL. The root app supplies server-authenticated owner identity to Budget; Budget supplies owner-scoped persistence and versioned saves; ORM supplies JDBC transaction and parameter-binding mechanisms. The supported production topology is a systemd Linux host with Caddy HTTPS termination, Jetty on 127.0.0.1:18083 and PostgreSQL on 127.0.0.1:5432. Local development uses scripts/run.sh; verification adds a disposable loopback TLS connector and disposable PostgreSQL. Migrations, backup/recovery and Maven publication are separate privileged operator workflows. Sources: README.md:3,28-36; application/src/main/webapp/WEB-INF/web.xml:5-25; application/src/main/java/org/financelab/app/BootstrapView.java:23-50; application/src/main/java/org/financelab/app/ApplicationLifecycle.java:32-42,56-63; ops/single-vm/finance-lab.service:7-20; ops/single-vm/Caddyfile:7-15; scripts/run.sh:10-25; scripts/verify.sh:53-84.

### Attacker Capabilities

- An unauthenticated internet client can request public pages/assets, obtain a login-form session and submit bounded credential attempts. It does not initially possess the owner password, authenticated session, operator files, loopback access or database/storage credentials. Filter/authentication failures could add owner-data read/write authority; this architecture pass does not assert such a failure.
- A malicious website can cause browser requests to the deployment. It does not initially know session CSRF tokens or gain same-origin script authority. Native account forms and transfer enforce different explicit CSRF/Origin controls; Vaadin dispatch is a separate dependency-owned control.
- A person or script controlling the guest browser profile or same origin can read/change its local budgets. That is an existing browser-storage authority, not evidence of a server authentication bypass. Guest data is untrusted when submitted for transfer.
- The configured authenticated owner can edit their budgets/catalog and request history/transfer through permitted commands. Multiple sessions of that same account share owner authority and can create version conflicts. The model does not invent a second supported login account or treat ordinary owner edits as privilege escalation.
- A client controlling an already authenticated browser can supply malformed JSON/form values to planner and transfer parsers, but does not thereby select a different server owner, acquire migration credentials or gain backup/operator authority.
- A bucket reader without the age recovery identity receives ciphertext. A backup service compromise carries database-read and configured storage/mail authority, independently of application login. The actual bucket write/delete capabilities require deployed IAM evidence.
- An OS/root/release/recovery operator already controls privileged configuration, executable releases or recovery database administration. Replacing trusted files or restoring a deliberately selected trusted archive under that authority is not by itself a new remote attacker capability.
